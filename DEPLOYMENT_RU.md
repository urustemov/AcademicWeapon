# Academic Weapon: развёртывание и эксплуатация

## Назначение документа

Документ предназначен для AUCA IT, владельца сервиса и технических
администраторов. Он описывает текущее окружение, конфигурацию доступа,
публикацию обновлений, работу с данными и контрольные проверки. Это не
инструкция для конечных пользователей.

## 1. Текущее окружение

| Параметр | Значение |
|---|---|
| Render Blueprint | `academic-weapon-staging` |
| Web Service | `academic-weapon-staging` |
| Репозиторий | `urustemov/AcademicWeapon`, ветка `main` |
| Регион | Frankfurt |
| Runtime | Python 3.15 / FastAPI / Uvicorn |
| Compute | 0.5 CPU, 512 MB RAM, один экземпляр |
| Постоянный диск | 1 GB, `/var/data` |
| База | `/var/data/academic_weapon.sqlite3` |
| Health check | `/healthz` |
| Render URL | `https://academic-weapon-staging.onrender.com` |
| Custom domain | `https://advising.auca.kg` — активен, основной адрес |

Render автоматически синхронизирует изменения `render.yaml` из `main` и
выполняет новое развёртывание. Постоянный диск сохраняется между сборками и
перезапусками.

## 2. Конфигурация и секреты

Production использует следующие переменные окружения:

| Переменная | Назначение | Хранение |
|---|---|---|
| `APP_ENV=production` | Включает production-проверки | `render.yaml` |
| `APSS_DEMO_MODE=0` | Запрещает demo-вход | `render.yaml` |
| `APSS_DB_PATH` | Путь к базе на постоянном диске | `render.yaml` |
| `GOOGLE_CLIENT_ID` | OAuth Web Client ID | Render Environment |
| `GOOGLE_WORKSPACE_DOMAIN=auca.kg` | Ограничение Workspace | `render.yaml` |
| `SESSION_SECRET` | Подпись серверных сессий | Генерируется Render |
| `SESSION_COOKIE_SECURE=1` | Secure cookies | `render.yaml` |
| `ALLOWED_HOSTS` | Разрешённые публичные hostnames | `render.yaml` |
| `CANONICAL_HOST` | Единственный пользовательский домен | `render.yaml` |
| `CANONICAL_ALIAS_HOSTS` | Технический Render-адрес для перенаправления | `render.yaml` |
| `ACADEMIC_TIMEZONE=Asia/Bishkek` | Академический часовой пояс | `render.yaml` |

`SESSION_SECRET`, рабочая SQLite-база, `.env` и исходные таблицы импорта не
должны храниться в GitHub. Google Client ID не является паролем, но управляется
как параметр окружения. Client Secret этому потоку Google Identity Services не
требуется.

## 3. DNS и HTTPS

Для адреса `advising.auca.kg` требуется запись в DNS-зоне AUCA:

| Поле | Значение |
|---|---|
| Type | `CNAME` |
| Name | `advising` |
| Target | `academic-weapon-staging.onrender.com` |

DNS настроен, Render подтвердил домен и выпустил TLS-сертификат. Основной адрес
портала — `https://advising.auca.kg`. Технический Render URL оставлен для health
check, но пользовательские запросы с него перенаправляются на официальный домен.

## 4. Google OAuth

OAuth Web Client использует официальный адрес портала.

**Authorized JavaScript origins**

```text
https://advising.auca.kg
```

**Authorized redirect URIs**

```text
https://advising.auca.kg/auth/google
```

Redirect URI должен совпадать с фактическим адресом посимвольно. После
изменения Google Cloud конфигурации распространение может занять несколько
минут. Локальные URI могут сохраняться только для контролируемой среды
разработки.

## 5. Выпуск обновлений

Стандартный цикл выпуска:

1. Изменение проходит локальные тесты.
2. В commit не входят `.env`, базы, импортируемые таблицы или токены.
3. Commit отправляется в `main`.
4. Render автоматически собирает и разворачивает новую версию.
5. Статусы Build и Deploy проверяются в Render Dashboard.
6. После статуса **Live** проверяются `/healthz`, вход, выход и ключевые права.

Неуспешная сборка не должна заменять последнюю работающую версию. При
регрессии используется rollback к последнему успешному deploy в Render, после
чего причина исправляется отдельным commit.

## 6. Контрольная проверка после deploy

- HTTPS работает без предупреждений браузера.
- `/healthz` возвращает `200` и не раскрывает пользовательские данные.
- Неизвестный Google-аккаунт получает отказ в доступе.
- Student не может открыть данные другого студента.
- Advisor видит только назначенных advisees.
- Advising Team не получает доступ к приватным диалогам, в которых не участвует.
- Групповой чат Advising Team доступен только четырём утверждённым аккаунтам.
- Встречу может изменять только её владелец согласно роли.
- Cookies имеют атрибуты `Secure`, `HttpOnly` и `SameSite=Lax`.
- Ответы содержат HSTS, CSP, `X-Content-Type-Options` и `X-Frame-Options`.
- Журналы не содержат токенов, паролей и текста приватных сообщений.

## 7. Данные, резервное копирование и восстановление

Рабочие данные размещаются только на постоянном диске `/var/data`. Перед
первичным переносом, обновлением схемы и минимум раз в неделю во время пилота
создаётся отдельная резервная копия базы. Передача выполняется через защищённый
канал Render; GitHub и обычная электронная почта для этого не используются.

Для согласованной копии используется встроенный SQLite backup API:

```bash
python backup_database.py --source /var/data/academic_weapon.sqlite3 \
  --output-dir /var/data/backups --keep 14
```

Скрипт проверяет исходную базу и готовый snapshot, использует закрытые права
файлов и удаляет только старые копии сверх заданного количества. Простое
копирование активного SQLite-файла запрещено. Не реже одного раза в месяц копия
восстанавливается в изолированной среде и повторно проверяются три роли. Копии
на том же диске недостаточно при отказе диска, поэтому актуальный проверенный
snapshot также хранится в одобренном AUCA IT защищённом хранилище.

Импорт студентов ограничен минимально необходимыми полями. Телефоны,
counseling notes, история контактов и свободные комментарии из исходной таблицы
не импортируются.

## 8. Мониторинг и инциденты

Для первичной диагностики используются Render Events, Logs, Metrics и
`/healthz`. При подозрении на компрометацию:

1. ограничивается доступ к сервису;
2. сохраняются технические журналы без распространения персональных данных;
3. ротируется `SESSION_SECRET`, что завершает существующие сессии;
4. проверяются изменения OAuth, allowlist пользователей и последние deploy;
5. при необходимости восстанавливается проверенная резервная копия;
6. инцидент документируется по процедурам AUCA IT.

## 9. Ограничения пилота и production-ready

Текущая схема — один сервер и SQLite — подходит для ограниченного пилота, но не
для широкого многопользовательского production. До масштабирования необходимы:

- миграция в управляемую PostgreSQL;
- автоматизированные проверяемые backups и регулярный restore test;
- утверждённые сроки хранения и удаления персональных данных;
- назначенные владельцы доступа, инцидентов и обновлений;
- независимая security review и устранение выявленных замечаний;
- документированный процесс onboarding/offboarding пользователей;
- мониторинг доступности и оповещения ответственных сотрудников.

Перенос реальных данных и выдача ссылки студентам выполняются только после
завершения контрольной проверки и согласования с AUCA IT.
